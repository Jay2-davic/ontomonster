# Maintaining OntoMonster Documentation

This guide is for developers and maintainers who update OntoMonster documentation.

## Keeping Screenshots Current

OntoMonster uses screenshots in the [User Guide](GUIDE.md) to help users complete tasks. Keep screenshots up to date when the UI changes.

### Automated Screenshots

Most screenshots are generated automatically using a Playwright script.

#### Setup

Install Playwright:
```bash
pip install playwright
python -m playwright install chromium
```

#### Generate Screenshots

```bash
# Generate all automated screenshots
python dev/capture_docs.py

# Generate specific groups only
python dev/capture_docs.py --only glossary menu
```

#### What the script does

1. Starts the OntoMonster UI (static HTML, no backend)
2. Stubs the API with sample data
3. Drives the UI through different states
4. Captures screenshots at each step
5. Saves PNG files to `docs/img/guide/`

#### How to capture manual screenshots

1. **Prepare your environment:**
   - Load CCO reference ontology
   - Create a test workspace
   - Have sample data files ready (CSV, XML, JSON, Parquet, data card)

2. **Use consistent settings:**
   - Browser window: 1280x800 or similar standard size
   - Clear browser cache before capturing
   - Use default theme (light mode)
   - Zoom level: 100%

3. **Capture the screens:**
   - Use your OS screenshot tool or browser DevTools
   - Crop to show only the relevant UI (not browser chrome)
   - Save as PNG with the exact filename from the list above
   - Place in `docs/img/guide/`

4. **Verify quality:**
   - Check that text is readable
   - Check that colors are accurate
   - Check that file size is reasonable (< 500KB per PNG)

### When to Update Screenshots

Update screenshots in these situations:

**Required updates:**
- After any UI change (layout, colors, fonts, controls)
- Before each major release (verify all screens are current)
- When functionality changes (new features, removed features)

**How to test:**
1. Run the automated script
2. Capture any changed manual screenshots
3. Build the documentation locally
4. Verify all images render correctly
5. Check that screenshots match the current UI

### Screenshot Guidelines

Follow these guidelines for consistency:

**Visual quality:**
- Use PNG format (not JPEG)
- Keep file sizes under 500KB
- Use standard browser window size
- Capture at 1x resolution (not retina/2x)

**Content:**
- Show only relevant UI (crop browser chrome)
- Use realistic but generic example data
- Never include sensitive information
- Use placeholder names: "myorg", "workspace1", "experiment1"

**Timing:**
- Capture after UI loads completely
- Wait for animations to finish
- Ensure dialogs are fully visible
- Check that all text has rendered

### Updating the User Guide

After updating screenshots:

1. **Verify references:**
   ```bash
   grep -r "img/guide/" docs/GUIDE.md
   ```
   Make sure all image references are correct.

2. **Check alt text:**
   Each image should have descriptive alt text:
   ```markdown
   ![Descriptive caption](img/guide/filename.png)
   ```

3. **Test locally:**
   Render the Markdown to verify images display correctly.

4. **Commit together:**
   Commit screenshot updates with the code changes that caused them:
   ```bash
   git add docs/img/guide/*.png
   git commit -m "Update screenshots for new import UI"
   ```

File: `CHANGELOG.md`

Update for every release:
- Follow Semantic Versioning
- Group changes by type (Added, Changed, Fixed, etc.)
- Write in ASD-STE-100 compliant language
- Date each release

## Documentation Standards

### Language

Use ASD-STE-100 Simplified Technical English:
- Short sentences (15-20 words max)
- Simple words
- Active voice
- Present tense
- One instruction per sentence

### Formatting

**Headings:**
- Use sentence case: "How to export" not "How To Export"
- Be specific: "Create a new workspace" not "Creating workspaces"

**Lists:**
- Use bullets for options
- Use numbers for steps
- Keep items parallel in structure

**Code blocks:**
- Always specify the language: ` ```bash `
- Include comments for complex commands
- Show expected output when helpful

**Links:**
- Use descriptive link text: [User Guide](GUIDE.md) not [click here](GUIDE.md)
- Verify all links after moving files

## Testing Documentation

Before releasing documentation:

1. **Read through as a new user:**
   - Can you complete each task with just the guide?
   - Are steps in logical order?
   - Are screenshots helpful?

2. **Check all links:**
   ```bash
   # Find all Markdown links
   grep -r "\[.*\](.*)" docs/
   ```

3. **Verify all images load:**
   ```bash
   # Find all image references
   grep -r "!\[.*\](.*)" docs/
   ```

4. **Test code examples:**
   - Run every command shown in the docs
   - Verify output matches what's documented

5. **Check for broken references:**
   - File paths that no longer exist
   - Section anchors that moved
   - External links that changed
